# Topic comments pagination

## Diagnosis and request trace

The shared presenter keeps comments in descending ID order, irrespective of the display preference. `firstCommentInList` is its oldest item (last array element), `lastCommentInList` its newest (index zero). The helpers in CommentsFragment/LoadMoreFooterHelperComment only render presenter state; they do not perform requests.

Before this change, older pages used `offset=1, count=20, start_comment_id=<oldest>, sort=desc`; newer pages used `offset=0, count=20, start_comment_id=<newest>, sort=asc`. CommentsApi sent these through execute to board.getComments, with a positive group_id and topic_id. It also requested first_id/last_id with two extra calls. The interactor sorted all returned items by descending ID and cached them; the presenter unconditionally removed the last item of newer pages, assuming it was the cursor. Availability depended only on first_id/last_id, so an empty/repeated page left the same cursor and enabled the same request again.

There is a second independently demonstrable failure: VKResponse did not deserialize execute_errors. The custom adapter intentionally accepts `main:false`, and the interactor mapped a missing main to an empty list. A failed internal board call therefore looked like a successful empty page, preserving the loop. The older fix/topic-load-more branch already attempted topic offsets but based them on UI list size, which is not a raw API position after deduplication, focused loading, or local edits.

The official parameter schema is https://github.com/VKCOM/vk-api-schema/blob/master/board/methods.json (board.getComments). It documents offset/count subsets and asc/desc. It does not specify wall-compatible cursor inclusion semantics. This change avoids depending on those semantics for continuation. No live authenticated VK response was captured; the precise server-side trigger for the reported device cannot be proven from this environment.

## Changed behavior

Only topic continuation uses independent raw offsets for asc and desc. Normal initial loading consumes offset zero in the chosen direction and marks the opposite edge reached. A focused initial request preserves the existing focus behavior; subsequent scans start at offset zero in each direction and skip already loaded identities automatically. Requests advance by raw item count, not the deduplicated UI size or numerical comment IDs. Duplicate-only pages are consumed within the same loading operation. Empty pages before the advertised end and identical consecutive pages raise retryable errors; failed requests do not commit their offset. Exhaustion uses the response count, not a short-page heuristic. Topic merging removes duplicate IDs, preserves all other rows, and restores descending internal order. API errors reach the existing error UI. The unused topic first/last probes are removed, including unsafe indexing into empty responses.

Post/photo/video cursor requests and merge branches are unchanged. The pagination changes do not modify authentication. At the user's explicit integration request, this branch also includes DirectAuthIdVKPresenter.kt byte-for-byte from fix/login-sid-invalid at 2d174591d35e3cc50db22bba047b47a439d09e30 (SHA256 fed19e70056512dbf49863323f267d423d27c4877a500bd0c4e77d0dd502ccb4). CI checks that the debug DEX contains both DirectAuthIdVKPresenter and TopicCommentsPager and records source hashes with the APK metadata. Cache writes retain their existing behavior; raw metadata is captured before model transformation.

## Validation and limits

Run `bash gradlew -p pagination-tests test`. This standalone JVM project compiles the production TopicCommentsPager without the unrelated native library. Its deterministic fixtures cover initial/second/third pages, both sort directions, raw-vs-unique counts, cursor overlap, focused scans, empty results, exhaustion, retry state, repeated server pages and nonconsecutive/deleted IDs. These are unit tests, not live VK integration or Android UI tests. Regression checks for post/photo/video are source isolation plus full application compilation, not a live functional test of those methods.

Run `bash gradlew :app_fenrir:assembleFenrirDebug` with a compatible AAR in compiled_native. The GitHub workflow uses the README's source-native variant in its disposable checkout, builds FFmpeg 9.0 with the pinned NDK, enables :native, runs the JVM tests, and uploads the native AAR and APK. Tool versions come from the repository catalog; the daemon requires Java 25, source compatibility Java 21.

Offset pagination cannot provide snapshot isolation if VK removes earlier comments or inserts rows into the sorted prefix between requests. Duplicate suppression handles overlap, but a concurrent deletion before the current offset can still shift an unseen comment behind that offset. Refresh restarts the scan. A stronger guarantee needs a server snapshot/cursor contract or reconciliation scans; it is not claimed here. Focus lookup still uses the existing initial cursor and deep-search path. Device verification against an authenticated topic, concurrent-mutation tests, and end-to-end presenter/API tests remain necessary before claiming complete functional resolution.
